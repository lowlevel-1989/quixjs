# binding

English | [Español](README.es.md)

The browser APIs for the JS of the game, written as classes and functions of
the engine layer (`js/js.h`, on JavaScriptCore). Each file adds its part to
the global object with a `js_api_add_*()` function that `core/main.c` calls at start; the order matters (events
and the base DOM before canvas and images). The drawing itself is in `gfx/`,
the audio in `audio/` and the window and input in `backend/`.

| file                 | what it does |
|----------------------|--------------|
| `window.c`           | `window` (the same object as `globalThis`), `innerWidth` / `innerHeight` from the toml of the game, `location` (`http://localhost/`) |
| `document.c`         | minimal DOM: elements, appendChild, getElementById, getElementsByTagName; the canvases added to the document are the ones on screen |
| `events.c`           | EventTarget, Event, KeyboardEvent, MouseEvent, CustomEvent; events dispatched in the next turn of the loop |
| `timer.c`            | setTimeout, setInterval, requestAnimationFrame, `performance.now()` (on top of `core/timer.c`) |
| `canvas.c`           | HTMLCanvasElement: its RGBA framebuffer, width, height, getContext (one type of context per canvas); a canvas created inside a `gpu-canvas` hook draws on the GPU (`gfx/gpu2d.c`) |
| `canvas/2d/`         | CanvasRenderingContext2D, one file per topic ([README](canvas/2d/README.md)) |
| `webgl.c`            | WebGL 1 on OpenGL ES 2.0 (`gfx/gl.c`): each canvas draws in its own framebuffer. An index file: it joins the parts of `webgl/` and is compiled as one ([README](webgl/README.md)) |
| `video.c`            | `__quixVideo` on `video/` (open, info, state, play, pause, close, volume, visible, `supported`); up to 4 videos, the visible one goes on screen |
| `webgl_constants.h`  | WebGL 1 constants, generated by `tools/gen_gl.py` (do not edit by hand) |
| `image.c`            | Image / HTMLImageElement: decodes when `src` is set, load / error in the next turn |
| `blob.c`             | Blob and `URL.createObjectURL`: the bytes stay in C and Image and XHR read the `blob:` url without copies |
| `xhr.c`              | XMLHttpRequest for the local files of the game (text, json, arraybuffer; `blob` gives an ArrayBuffer); no network |
| `script.c`           | `<script>` added with appendChild, `document.currentScript`, DOMContentLoaded and load |
| `audio.c`            | WebAudio on the mixer of `audio/`: the natives (`__quixAudio`) |
| `webaudio.js`        | the WebAudio graph in JS (AudioContext, decodeAudioData, gain and panner nodes) |
| `navigator.c`        | `navigator` and `getGamepads()` (4 slots, "standard" mapping) |
| `gamepads.js`        | `getGamepads()` in JS, on the state `navigator.c` reads from the backend |
| `nwjs.c`             | nw.js mode: the natives of `fs` |
| `nwjs/`              | nw.js mode in JS, one file per Node module: `require('fs')`, `path`, `events`, `os`, `nw.gui`, `process`, greenworks ([README](nwjs/README.md)) |
| `quix.c`             | the `quix` object: `exit`, `pressKey`, `frame`, `backend`, `fixedStep`, `registerFont`, `hasFont`, `version`, `frameTime`, `achievementUnlocked`, `achievements`, `achievementsIcon`, `isGpuCanvas`, `collectGarbage`, `gcPressure` |
| `console.c`          | `console` (log, info, warn, error...) and `print` |
| `polyfill.c`         | runs the APIs written in JS of `polyfill/` at start |
| `polyfill/`          | the APIs written in JS, one file each ([README](polyfill/README.md)) |

## JS files

The `.js` files of this folder (and `polyfill/`) are part of quixjs, written
in JS. They are not read at run time: `tools/embed_js.py` turns each one into
a C string at build time and its `.c` runs it at start. That way the JS is
edited as JS and quixjs stays a single program, with no files to look for.

## C or JS

It goes in C when:

1. It touches something native: the GPU (`webgl.c`, `canvas/2d`), files
   (`xhr.c`, `image.c`), the SDL audio (`audio.c`), the video decoder
   (`video.c`), the gamepads (`navigator.c`) or the TTF fonts
   (`quix.fonts.register`).
2. It is called many times per frame: `drawImage`, `fillRect` or
   `drawElements`. Each call from JS to C costs, but doing the work in JS
   costs much more. That is why the engine hooks move things like the blur or
   the tint to C.
3. It needs data only C has: the size of the window, the clock or the state
   of the backend.

It goes in JS ([polyfill](polyfill/README.md)) when:

1. It is logic that only uses other APIs that already exist: `localStorage`
   is an object in memory, and `atob` / `btoa` is string arithmetic.
2. It is "browser shape": objects, properties, promises and events the game
   expects to see, like `FontFace.loaded`, the `loadeddata` / `ended` events
   of `<video>`, `screen` or `matchMedia`. In C it would be a lot of code of
   the JavaScriptCore API for something that in JS is a few lines.
3. It is called rarely: at start or at odd moments, without its cost showing
   in the frame.

## Images encrypted by RPG Maker

RPG Maker MV decrypts its images with its own code and gives them to Image as
a `blob:` url. `blob.c` keeps the bytes in C with a reference counter, so the
url `blob:quix/N` from `createObjectURL` can be read by Image and
XMLHttpRequest without copying the data back to JS.

With the hook `rpgmaker-mv/decrypt-image-native` the image gets the
encrypted path, and quixjs reads it, decrypts it (key of `$dataSystem`) and
decodes it in the background: the bytes do not go through JS.

## nw.js mode

With `[engine] nwjs = true` in the toml of the game, `nwjs.c` adds the minimum that
games made for nw.js use (RPG Maker MV saves with `fs` in `www/save/`).
Relative paths are relative to `game_dir`, and `require('./x')` loads `x.js`
as a CommonJS module. Native modules (`.node`) and modules that do not exist
return a substitute whose functions return false, like a game without Steam
open.

## WebGL

All WebGL contexts share one GL context: in practice a game uses one (PIXI
creates a test one and drops it). When the result has to be seen in memory
(drawImage, screenshots, the dummy backend) it is read with `glReadPixels`
into the surface of the canvas. With the sdl backend the texture of the canvas
goes straight to the screen. `--no-webgl` or `webgl = false` make
`getContext("webgl")` return null, so the game uses its canvas renderer.

## WebGL buffers

`bufferSubData` from offset 0 on a `STREAM_DRAW` or `DYNAMIC_DRAW` buffer
(the sprite batches of PIXI) asks for new memory first with `bufferData`
(orphaning). Without it the driver waits until the GPU stops using the buffer
(about 1.6 ms each time on panfrost). The data after the written part is
lost; with those usages it is written again before drawing.
